## Session summary

### What we were trying to do
Get the Mac II core far enough into boot that the Slot Manager probes the
NuBus video card and we see pixels on screen. The 11-day-old memory note
said we were stuck at a BTST #5 loop at `$40806DD8`.

### What we discovered

1. **`debug_cpuIPL` is active-low.** Old notes called `IPL 7→6` an "NMI
   storm"; it's actually a normal IPL 0→1 (VIA1 tick). Not a problem.

2. **The BTST #5 loop is normal ROM behavior.** `$40806DCC: BSET #5,$015D(A3)`
   sets the flag, then the code enters `$40806DD8: BTST #5,$015D(A3) / BNE $40806DD8`.
   The loop exits when the VIA1 SR-complete interrupt handler at `$40807002`
   clears the bit. Snow works the same way.

3. **We traced Snow's instruction flow** for comparison. Built a custom
   Rust tool at `tools/snow_trace/` that uses `snow_core` as a library to
   dump instruction history to a file. It uses Stop/Run pulses to force
   periodic history drains from the emulator. See
   `tools/snow_trace/src/main.rs`. Runs as:
   ```
   cd tools/snow_trace
   ./target/release/snow_trace ../../releases/boot0.rom ../../releases/boot2.rom 200000000 /tmp/snow_trace.log
   ```
   - **boot0.rom** = Mac II boot ROM (hash
     `97f2a22bdb8972bfcc1f16aff1ebbe157887c26787a1c81747a9842fa7b97a06`)
   - **boot2.rom** = Macintosh Display Card 8·24 ROM (341-0868) — **this
     is what Snow requires**. Snow does NOT support the 341-0660 hi-res card
     we use in the FPGA core (our `boot1.rom`). For main-ROM boot behavior
     the two are equivalent since the ROM is stuck well before slot-probe.
   - **Model is forced to `MacModel::MacII`** (not FDHD) in the trace tool.
   - Default Mac II RAM size is 8 MB in both Snow and our sim; no mismatch.

4. **The SCC diagnostic loop is a downstream symptom, not the real bug.**
   When the VIA1 SR handler doesn't fire, the BTST #5 loop never exits
   cleanly. Eventually the ROM ends up spinning in a serial-diagnostic
   poll loop at `$40802EDC-$40803284` waiting for a character that never
   arrives. Fixing the SR handler also fixes this.

5. **The root cause of the VIA SR failure:** Our VIA6522 shift register
   needs 8 CB1 clock edges to complete a byte. CB1 is generated by
   `kbdclk` in `dataController_top.sv`, which only toggles when
   `kbd_transmitting` is set, which only starts on the rising edge of
   `via1_sr_active` — which in turn requires the VIA's internal shift
   register to be armed via `trigger_serial`/`trigger_acr_shift` on a
   `falling` edge coinciding with `wen`. This is a chicken-and-egg chain
   with fragile timing.

6. **In Snow, the shift register is entirely software-timer-based.** Snow's
   `core/src/mac/via.rs` (around line 431 and 568) does not emulate CB1
   edges at all — it simply sets `kbdshift_out_time = SHIFT_DELAY` (~3ms)
   when SR is written in shift-out mode (or when ACR changes to shift-out
   mode), counts down, then at expiry delivers the byte to the ADB
   transceiver and sets IFR bit 2 (SR complete).

7. **We implemented Snow's approach as a bypass** in
   `dataController_top.sv`. See the block starting around line 404
   labeled "Snow-style timer-based VIA1 shift register completion". It:
   - Detects VIA1 SR/ACR writes at the bus level
     (`selectVIA && !_cpuVMA && !_cpuRW` with `cpuAddrRegHi==A` or `B`).
     This avoids the verilator `wen`/`falling` timing pitfall.
   - Starts a ~100K-clock timer (~3ms at 32.5 MHz) when a shift-out or
     shift-in mode is entered.
   - On expiry, pulses `via1_sr_ext_complete` → the VIA accepts it as
     "shift done", sets IFR bit 2, and clears `shift_active`.
   - For shift-out, also pulses `via1_sr_out_done` which causes the
     keyboard-control block to drive `adb_din_strobe`/`adb_din` so the
     ADB transceiver receives the command byte.
   - For shift-in, loads `kbd_to_mac` into the VIA's `shift_reg` via
     `sr_ext_load`/`sr_ext_data`.
   - New VIA6522 ports: `sr_ext_complete`, `sr_ext_load`, `sr_ext_data`
     (see `rtl/via6522.sv` line ~60 and the handler near the bottom of
     the `shift_active` always block).

## Important discoveries to carry forward

### The "$display" to stderr trap
`$display` output from Verilog goes to **stdout**, not stderr. I spent
hours assuming zero output meant the block wasn't firing because I was
grepping stderr. If you add `$display` debug to VIA or other Verilog
modules, redirect stdout separately:
```
./obj_dir/Vemu --headless --stop-at-frame 100 > /tmp/out.log 2>/tmp/err.log
grep "VIA_" /tmp/out.log
```

### `wen && falling` inside the VIA6522
During debugging I chased a hypothesis that `wen` and `falling` never
overlap in verilator. **This was wrong** — they do overlap, the debug
output was just going to stdout. Do NOT reintroduce the `wen_s`/`ren_s`
or trigger_acr_shift_pending workarounds; they add either an extra cycle
of delay or fire twice, both of which would be wrong on real FPGA.

### E-clock timing reference
In `rtl/tg68k/tg68k.v`:
- `eCntr` counts 0-9 (10 states per E cycle)
- `eCntr == 5`: E goes high → `E_PosClkEn`
- `eCntr == 9`: E goes low → `E_NegClkEn`
- `eCntr == 3`: VMA asserted (if VPA was sampled low)
- `eCntr == 0`: VMA deasserted

In `verilator/sim.v` lines 359-360:
```verilog
.E_PosClkEn ( tg68_E_falling ),  // eCntr==5, E rising edge
.E_NegClkEn ( tg68_E_rising  ),  // eCntr==9, E falling edge
```
The names are swapped (VIA `falling` = E rising). This is confusing but
not wrong — just unconventional. VIA6522 writes happen on the E rising
edge (eCntr==5) = our `falling` signal. VMA is active from eCntr=3 to
eCntr=0, so it spans both edges.

### `$015F(A3)` and `$015D(A3)` flag bytes
The ROM uses these RAM flag bytes around the ADB/VIA-SR code:
- `$015C(A3)` — ADB transaction status; bits 2-3 = 00 (idle), 08 (listen),
  0C (talk). Handler at `$40807002` dispatches based on these bits.
- `$015D(A3)` bit 0 — set by `$408073E6` (BSET #0,$015D) at start of ADB
  shift-out. Cleared by `$40807028: BTST #5,$015D(A3) / BNE $40807100`
  path.
- `$015D(A3)` bit 5 — THE bit polled by the BTST #5 loop at `$40806DD8`.
  Set by `$40806DCC: BSET #5,$015D(A3)`. Cleared somewhere in the CA1
  handler code path.
- `$015E(A3)` — state byte, various bits cleared/set by handlers.
- `$015F(A3)` bit 0 — set by `$408073A2→$408073C0→BSET D0,$015F(A3)` with
  D0=0. Checked by `$40807020: BTST #0,$015F(A3)`.

### Next VIA1 handler decision point
The handler at `$40807002` currently takes this path in our sim:
```
$40807002: MOVE.B #$04,$1A00(A1)   ; clear VIA IFR bit 2 (SR complete)
$40807008: MOVEA.L $0CF8.W,A3      ; load ADB globals ptr
$4080700C: MOVE.B $015C(A3),D0
$40807010: ANDI.B #$0C,D0          ; mask bits 2-3
$40807014: CMPI.B #$08,D0          ; =$08 (listen)?
$40807018: BEQ.S  $40807036        ; → bit-0-$015F handler
$4080701A: CMPI.B #$0C,D0          ; =$0C (talk)?
$4080701E: BEQ.S  $40807036        ; → bit-0-$015F handler
$40807020: BTST   #0,$015F(A3)     ; fall-through path
$40807026: BNE.S  $40807092        ; → receive complete handler
$40807028: BTST   #5,$015D(A3)     ; fall-through
$4080702E: BNE.W  $40807100        ; → exit via JMP(A0)
```
In Snow, the path is `$40807020 → $40807026 (BNE not taken) → $40807028 →
$4080702E (BNE taken) → $40807100`. So Snow sees `$015F` bit 0 **clear**
at the handler entry, and `$015D` bit 5 **set**.

In our sim we don't know the branch direction with certainty — my
instrumentation was just printing "reached this PC" not "branch taken".
**Next session should add proper branch-direction instrumentation** by
reading the next PC after `$40807026` and `$4080702E`.

## Reference: key boot flow
```
$40806DCC: BSET #5,$015D(A3)        ; set flag
$40806DD2: BSR  $40806DEA            ; ADB init
$40806DD4: ANDI #$F8FF,SR            ; enable interrupts
$40806DD8: BTST #5,$015D(A3)         ; poll...
$40806DDE: BNE.S $40806DD8           ; ...wait for clear
$40806DE0: JSR  $408077F4            ; (after exit) next step
```

ADB init subroutine at `$40806DEA`:
```
$40806DFC: MOVE.B D0,$015C(A3)       ; zero status
$40806E00: MOVE.B #$08,$0163(A3)     ; mode flag
$40806E06: MOVE.B #$30,$015E(A3)     ; state
$40806E0C: BSR  $408073E6            ; VIA1 SR shift-out setup
$40806E10: BSR  $408073A2            ; VIA1 ACR shift-disable + $015F
$40806E14: RTS
```
