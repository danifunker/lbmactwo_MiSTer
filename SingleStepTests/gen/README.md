# FPU oracle + hardware bench

End-to-end pipeline for verifying 68881 FPU behavior across three
environments: a software oracle (MAME's m68kfpu), a real Macintosh II,
and (when wired up) the verilator build of `mc68881_top`. All three
emit results in the same JSON-Lines schema so any pair can be diffed
with the same `diff_corpus.py` tool.

```
   +-----------+    +----------+    +----------------+    +-----------+
   | mame_fpu_ |    |  Snow    |    | fpu_test_      |    | cpu_fpu/  |
   | capture   |    | emulator |    | macii_full.c   |    | verilator |
   | .lua      |    | (same    |    | (Mac OS app)   |    | (TODO)    |
   |           |    | .APPL)   |    |                |    |           |
   +-----+-----+    +-----+----+    +--------+-------+    +-----+-----+
         |                |                  |                  |
         v                v                  v                  v
   fpu_corpus.json   fpu_snow.jsonl    FPU Results        fpu_verilator
                                       Full.jsonl         .jsonl
                       \      |        /            /
                        \     |       /            /
                         v    v      v            v
                    +---------------------------------+
                    |       diff_corpus.py            |
                    | (categorizes divergences,       |
                    |  outputs terminal/json/markdown)|
                    +---------------------------------+
                                  |
                                  v
                       SingleStepTests/results/*.md
                       SingleStepTests/results/*.json
```

## Files in this directory

### Test generator + oracle

- `mame_fpu_capture.lua` — drives MAME's `maciihmu` driver via Lua.
  Builds a 270-test corpus across dyadic, monadic, and transcendental
  ops, runs each test in the live CPU, and writes:
  - `/tmp/fpu_corpus.json` — JSON Lines, one test per line, initial +
    final state for every test
  - `/tmp/fpu_tests.h` — C header with the same test specs as a
    static `FpuTestSpec[]` array (consumed by the Mac program)
- `mame_fpu_capture_9smoke.lua` — same machinery but only the nine
  original hand-coded smoke tests. Used to confirm hardware-vs-MAME
  semantics didn't shift across an upstream MAME rebuild.
- `gen.c` + `Makefile` — Musashi-based CPU corpus generator (for the
  `tg68k/` bench). Not FPU-related.

### Mac OS application

- `fpu_test_macii.c` / `.macc` — original 9-test bench, hand-coded
  test list inline. Useful as a minimal smoke check on real hardware.
- `fpu_test_macii_full.c` / `.macc` — full 270-test bench. `#include`s
  `fpu_tests.h` and iterates `g_fpu_tests[]`. Output: `FPU Results
  Full.jsonl` in JSONL form matching the MAME oracle's schema, so the
  two files diff line-by-line.
- `fpu_tests.h` / `.macc` — auto-generated by `mame_fpu_capture.lua`.
  Do NOT edit by hand.
- `fpu_tests_q{1..4}.h` / `.macc` — corpus split into four ~67-test
  slices. Each slice header overrides `FPU_OUTPUT_PATH` so swapping
  headers retargets the output file automatically. Useful if a build
  pushes past THINK C's 32KB globals limit (one slice is ~17KB).

The `.macc` twins are byte-identical to the `.c`/`.h` files except
that they use `\r` (CR) line endings, which classic Mac OS expects.
Transfer the `.macc` file to the Mac, rename to `.c`/`.h` on the
Mac side, then build.

### Diff / analysis tool

- `diff_corpus.py` — compares two JSONL corpora and categorizes the
  divergences. Three output modes:
  - default (no flag): human-readable terminal report
  - `--json`: machine-parseable structured dump for CI / tooling
  - `--markdown`: drop-in markdown for documentation

  Categories: `match`, `trailing_bits`, `nan_encoding`,
  `inf_handling`, `special_value`, `cc_only`, `smoke_fpinit`,
  `unknown`.

## Test schema (JSON Lines)

Every output file is one JSON object per line, schema:

```json
{
  "name": "FADD.X FP1,FP0 (pos_one,pos_two)",
  "initial": {
    "d":   [0,0,0,0,0,0,0,0],
    "a":   [0,0,0,0,0,0,0,2097152],
    "fp":  ["3fff0000800000000000....", ...],
    "fpcr": 0, "fpsr": 0, "fpiar": 0
  },
  "final": {
    "d":   [1,0,...],
    "a":   [...],
    "fp":  ["400000008000000000000000", ...],
    "fpcr": 0, "fpsr": 0, "fpiar": 0
  }
}
```

- `fp[]`: 8 strings, each 24 hex chars (12 bytes of extended-precision)
- `d[]`, `a[]`: 8 unsigned 32-bit integers
- `fpcr` / `fpsr` / `fpiar`: unsigned 32-bit integers

`diff_corpus.py` compares only the semantically-important post-test
fields (FP0, FPSR.CC byte, FPCR, D0). It deliberately ignores
FP1..FP7 in non-FMOVE tests (uninit reset state varies by
implementation), A0..A7 (Mac stack residue), and FPSR's AEXC/EXC/Q
bytes (sticky/cross-test bleed).

## Typical workflows

### Regenerate the oracle + header from scratch

```
cd /Users/dani/repos/mame
./maciihmu maciihmu -bios original -skip_gameinfo -debug \
    -debugger none -window -nothrottle -autoboot_delay 1 \
    -autoboot_script /Users/dani/repos/lbmactwo_MiSTer/\
SingleStepTests/gen/mame_fpu_capture.lua
```

Produces `/tmp/fpu_corpus.json` and `/tmp/fpu_tests.h`. Re-running is
the source of truth: any change to the test list in the `.lua` script
updates both files in lockstep.

### Compare a candidate corpus to the oracle

```
python3 SingleStepTests/gen/diff_corpus.py \
    /tmp/fpu_corpus.json /path/to/candidate.jsonl
```

Add `--markdown > SingleStepTests/results/<run>.md` to save a snapshot.
Add `--json > SingleStepTests/results/<run>.json` for tooling.

### Build the Mac OS bench

1. Transfer `fpu_test_macii_full.macc` and `fpu_tests.h.macc` to the
   Mac. Rename to `.c` / `.h`.
2. In THINK C: New Project → Application → add the `.c` file, plus
   `ANSI.π` and `MacTraps`. Place the `.h` file in the same folder
   (NOT the project picker — the picker takes source files and
   libraries only).
3. Project → Build Application → save as e.g. "FPU Test Full".
4. Run on a real 68020+68881 Macintosh. Output: `FPU Results
   Full.jsonl` in the app's directory.

If you hit "Could not evaluate constant expression" or a bus error
before the window appears, the globals/data segment is over 32KB.
Either enable 32-bit globals in THINK C's project type options, or
build with one of the `fpu_tests_q{1..4}.h` slice headers instead
(each is ~17KB and produces a separate `FPU Q<n>.jsonl` output).

## Baseline results

`SingleStepTests/results/hw_vs_mame_2026-05-16.md` is the first
documented baseline: real Mac II hardware (System 7.1.2 + 68881) vs
MAME's m68kfpu oracle. **170 / 270 tests (63%) match byte-for-byte**
on the compared fields.

Ops at 100% pass: FABS, FADD, FTST. Ops ≥80%: FCMP, FGETMAN, FMUL,
FNEG, FSGLMUL, FSCALE, FSQRT, FSUB. The 100 divergences are
concentrated in transcendentals (MAME softfloat vs real silicon
algorithms differ in the last 1-3 mantissa bits) and special-value
handling (NaN encoding, infinity inputs to FINT/FSGLDIV/etc).

See `SingleStepTests/test-blockers.md` for the full categorized list
and the bench-side issues still to fix (FPSR.AEXC reset, etc.).
