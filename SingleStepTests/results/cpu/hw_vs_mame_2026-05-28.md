# CPU corpus comparison — real Macintosh II vs MAME (2026-05-28)

Full 718-test CPU corpus, consolidated supervisor bench (`supervisor_bench`,
`make cpu`). This is the first run covering the **entire** corpus in one pass —
normal supervisor tests *and* the exception/TRAP tests — after the recovery
fixes (TRAP vectors 32–47 caught, autovector IRQs left to ROM, Line-A flagged
`hw_unsafe`).

- **Hardware:** real Mac II, full run, all 717 runnable tests completed and
  persisted to `/Results.jsonl` (`results/cpu/hw_2026-05-28.jsonl`).
- **MAME baseline:** instruction-level oracle from `gen/mame_cpu_capture.lua`
  on `maciihmu` (`results/cpu/mame_baseline_2026-05-28.json`, 718 lines).
- **Corpus parity:** the oracle's regenerated `cpu_tests.h` is byte-identical to
  the committed one except for one explanatory comment block — the *test bytes*
  the two sides executed are identical.

## The 37 non-exception divergences (all explainable)

Comparison excludes the **address registers**: the oracle and the Mac bench
deliberately preload A6 (and A7/USP) to *different* platform-specific scratch
bases (see the lua harness note), so absolute A-register values always differ
by design. Compared fields: `d[0..7]`, `ccr`, `ram`.

| Count | Bucket | Why it is not a bug |
|---:|---|---|
| 25 | Platform scratch-address dependent | Results that *are* an address: abs addressing (`(xxx).W/L=$18xx`), `PEA (A6)`, `EXG D,A`, `MOVE.L A6,D0`, memory-indirect `([bd,A6]…)`, `MOVEM` of A-regs. Different scratch base ⇒ different address value, same computation. |
| 6 | Undefined-flag edge cases | `DIVS/DIVU` overflow (Z/N undefined), `CMP2` (N undefined), `ABCD/NBCD` (V/N/Z undefined). The 68020 PRM leaves these CCR bits *undefined*; silicon and emulator may differ. |
| 4 | Control-reg / machine-state | `MOVEC VBR/SFC/DFC/CACR` — VBR differs because the bench installs its own vector table; SFC/DFC/CACR are live machine state. |
| 1 | SR system byte | `MOVE.W SR,(A6)` stores the live interrupt-mask (IPL) bits. |
| 1 | CCR capture timing | `ORI #imm,CCR` — capture-methodology artifact, not semantics. |

## Why the bench hangs in MAME at ~test 405 (but not on hardware)

When the consolidated bench is *booted as a disk* in MAME (`-hard1 .hda` or
`-flop1 .dsk`), it consistently freezes around **test 405 (`SUBI.W #0x1234,(A6)`)**
— on both disk types — while the real Mac II completes all 717.

It is **not a CPU-test failure**: the instruction-level oracle executes
`SUBI.W #0x1234,(A6)` correctly (it's one of the 660 matches), and the hung
bench had already recorded `vec=0` for it. The freeze is in the **disk write**,
not the CPU.

The mechanism is MAME's `maciihmu` disk driver, not our code:

- `jsonl_writer` flushes results to disk in 16 KB batches (32 sectors each).
- 404 result lines fit in the first 8 batches = **256 sectors** written cleanly.
- The 9th batch flush (starting at sector 256) hangs.
- This lines up with the documented MAME limit in `jsonl_writer.h`: the
  `maciihmu` SCSI driver has a *"too many rapid calls" threshold we hit at
  ~227 single-sector writes.* The 16 KB batching cut the `_Write` *call* count
  but not the underlying *sector* count, so a long-enough run (the full 717-test
  corpus) still crosses the threshold and the emulated driver stalls.
- It is deterministic and disk-type-independent (same test on SCSI and floppy),
  confirming it's a cumulative-write limit, not the instruction or the bench.

Real Mac II disk controllers have no such limit, so the hardware run completes
and persists all 717 results — which is exactly how this full comparison was
obtained. To get MAME's side for the full corpus we therefore use the
instruction-level oracle (no disk writes), not a disk boot.

### MAME tooling notes

- `maciihmu` headless **floppy** boot fails under `SDL_VIDEODRIVER=offscreen
  -video none` (black screen, video card never inits); the same `.dsk` boots in
  a windowed local MAME. SCSI `.hda` boots headless.
- rb-cli emits raw logical 800K images (boot on FloppyEmu hardware).
  `rb-cli convert … --format dc42` produces a valid DiskCopy 4.2; round-tripping
  back to `--format raw` is byte-identical.

## Reproduce

```
# Oracle (full 717, no disk):
cd ~/repos/mame
SDL_VIDEODRIVER=offscreen ./mame maciihmu -bios original -rompath ~/repos/mame/roms \
    -skip_gameinfo -debug -debugger none -nothrottle -autoboot_delay 1 \
    -autoboot_script .../SingleStepTests/gen/mame_cpu_capture.lua \
    -video none -seconds_to_run 900
# writes /tmp/cpu_corpus.json (oracle) + /tmp/cpu_tests.h

# Hardware: boot supervisor_bench/fixtures/cpubench.dsk on a real Mac II,
# extract /Results.jsonl via rb-cli.
```
